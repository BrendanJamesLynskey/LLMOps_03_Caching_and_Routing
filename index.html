Three Cache Layers — Exact, Semantic, Prompt Cache

LLM caching operates at three distinct layers. Understanding which layer applies to which use case prevents misapplication — each has a different failure mode and cost-saving profile.

Layer 1: Exact-match cache — hash(messages) → stored response
↓ miss
Layer 2: Semantic cache — embed(prompt) → cosine nearest neighbour → stored response
↓ miss
Layer 3: Prompt cache — provider-side KV cache reuse for shared prefix
↓ miss
Full generation — pay full input + output token cost
LayerHit conditionCost savingRisk
Exact matchSHA-256(serialised messages) matches100% — zero provider callStale responses; only works for identical inputs
SemanticCosine similarity > threshold (e.g. 0.97)100% — zero provider callWrong answer served for semantically-similar but different question
Prompt cacheShared prefix exists in provider KV cache50–90% on cached input tokens onlyCache miss on cold start; TTL-limited
When to use each layer

Exact match is safe for pure data retrieval prompts where the answer is deterministic (e.g. “classify this product category”). Semantic cache suits FAQ-style applications where paraphrases should return the same answer. Prompt cache is universally useful when you have a long system prompt or a large document prefix that repeats across requests.

Anthropic Prompt Caching — TTL, Breakpoints, Write Cost

Anthropic’s prompt caching (available on Claude 3 Haiku, Sonnet 3.5, Opus 3, Sonnet 3.5 v2, Haiku 3.5) caches KV activations server-side for a sliding window TTL. The cache is keyed on the exact byte sequence up to the breakpoint.

Python SDK — marking a cache breakpoint
response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": long_system_prompt,          # must be ≥ 1024 tokens
        "cache_control": {"type": "ephemeral"}  # place breakpoint here
    }],
    messages=[
        {"role": "user", "content": [
            {"type": "text", "text": full_document,
             "cache_control": {"type": "ephemeral"}},  # second breakpoint
            {"type": "text", "text": user_question}
        ]}
    ]
)
# response.usage carries:
# cache_creation_input_tokens  — tokens written to cache (1.25× cost)
# cache_read_input_tokens       — tokens served from cache (0.10× cost)
# input_tokens                  — uncached tokens (1.00× cost)
ParameterValue
TTL (sliding window)5 minutes after last hit (extended each time the cached prefix is used)
Minimum cacheable block1024 tokens for Claude 3 / 3.5; 2048 tokens for Claude 3 Haiku (lower limit)
Maximum breakpoints4 per request (system + up to 3 user/tool positions)
Cache write cost1.25× normal input token price
Cache read cost0.10× normal input token price
Break-evenCache write pays back if the same prefix is used >1.39× more often (write amortised over reads)
Ordering is critical

Cache keys are prefixes, not hashes of the full context. If request A caches tokens 1–4000 and request B starts with tokens 1–4000 but then diverges, B will hit the cache for its first 4000 tokens. Change the order of content within the cached section and the cache misses entirely. Keep static content (system prompts, documents) before dynamic content (user messages).

03

OpenAI Implicit Prompt Cache — How to Hit It

OpenAI implements prompt caching automatically — no cache_control markers required. The cache key is the first 1024 tokens of the prompt; any request that shares this prefix gets a cache discount on the matching tokens.

Mechanics

How OpenAI determines a hit

  • Prefix granularity is 128 tokens (the KV cache block size)
  • Cache applies to the longest matching prefix in steps of 128 tokens
  • TTL is 5–10 minutes (not published; empirically measured)
  • Only applies to gpt-4o, gpt-4o-mini, o1, o3, o4-mini as of 2025
  • Cache hit cost: 50% off on cached input tokens (zero flag needed)

How to maximise hit rate

  • Put static content first: system prompt, few-shot examples, document context
  • Put dynamic content last: user question, conversation history
  • Keep the static prefix >1024 tokens to make the 50% discount meaningful
  • Avoid shuffling few-shot examples — any order change invalidates the cached prefix
  • Watch usage.prompt_tokens_details.cached_tokens in the response
Python — reading cached token count from OpenAI response
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages
)
usage = response.usage
cached = usage.prompt_tokens_details.cached_tokens    # may be 0 on cold start
uncached = usage.prompt_tokens - cached
print(f"Cached: {cached}, Uncached: {uncached}, Total: {usage.prompt_tokens}")
# Log this to your cost tracker — cached tokens cost 50% less
Batch API and prompt cache

OpenAI’s Batch API (50% discount vs synchronous) and prompt caching stack: a cached prefix in a batch request receives both discounts. A 10 K-token system prompt repeated across 1000 batch requests: 50% batch discount × 50% cache discount = 25% of standard cost for those tokens. Structure your batch requests accordingly.

Semantic Cache — GPTCache & the Dangers

Semantic caching returns a cached response when the new prompt is semantically similar to a cached prompt — even if the text is different. GPTCache (pip install gptcache, v0.1.x) is the reference implementation.

GPTCache — minimal Redis-backed semantic cache
from gptcache import cache
from gptcache.adapter import openai
from gptcache.embedding import Onnx
from gptcache.manager import get_data_manager, CacheBase, VectorBase
from gptcache.similarity_evaluation import SearchDistanceEvaluation

encoder = Onnx()           # 22 MB ONNX model, ~2 ms CPU embed

cache.init(
    embedding_func=encoder.to_embeddings,
    data_manager=get_data_manager(
        CacheBase("redis", url="redis://localhost:6379"),
        VectorBase("faiss", dimension=768)  # or "redis" with HNSW
    ),
    similarity_evaluation=SearchDistanceEvaluation(),
    similarity_threshold=0.97,              # cosine distance < 0.03 = hit
)

# Drop-in replacement for openai.ChatCompletion
response = openai.ChatCompletion.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": user_query}]
)

The dangers — when semantic cache hurts

Threshold too low

“What is the capital of France?” → cache hit for “What was the historical capital of France before Paris?”. Different correct answer. Set threshold ≥0.97 for factual queries; 0.85 is only safe for classification tasks.

Stale factual data

Cached answer reflects knowledge at time of caching. For queries about current events or mutable data (“What is the price of X?”) semantic cache should be disabled or TTL set to minutes.

Personalised responses

Semantic cache is per-prompt by default. Two users asking the same question should not share a cached answer if the response depends on user context (account state, role, tier). Namespace the cache key by user segment or disable for personalised routes.

A production semantic cache needs a vector index that scales to millions of cached prompts and serves similarity lookups in <5 ms. Three Redis variants cover most use cases.

RedisVL — semantic cache with metadata filter
from redisvl.extensions.llmcache import SemanticCache
from redisvl.utils.vectorize import OpenAITextVectorizer

cache = SemanticCache(
    name="llm-cache",
    redis_url="redis://localhost:6379",
    vectorizer=OpenAITextVectorizer(model="text-embedding-3-small"),
    distance_threshold=0.03,       # cosine distance (lower = stricter)
    ttl=3600                         # 1 hour TTL
)

hit = cache.check(prompt=user_query,
                   vector=cached_embedding,   # reuse embed from retrieval step
                   filter_expression=f"@tenant:{tenant_id}")
if hit:
    return hit[0]["response"]

response = call_llm(user_query)
cache.store(prompt=user_query, response=response,
            metadata={"tenant": tenant_id, "model": "gpt-4o"})
Embedding model consistency

Cache misses spike if you change the embedding model: a text-embedding-ada-002 vector and a text-embedding-3-small vector for the same text are not comparable. Version-stamp your cache namespace by embedding model (llm-cache:te3s:v1) and warm the new namespace before switching.

Routing Patterns — Capability, Cost, Latency

Routing decides which model receives a request. The decision can be static (rule-based) or dynamic (measured at runtime). Three orthogonal routing dimensions apply to most production systems.

Capability routing

Route by what the model can do: context window, vision support, tool-calling, structured output, language. Examples:

  • Request with image → vision-capable model
  • Prompt >100 K tokens → 200 K context model
  • Requires JSON schema output → model with reliable structured output
  • Non-English query → model with that language in training

Cost routing

Route simple tasks to cheap models. A query classifier (a small LLM or a fine-tuned BERT) tags requests as simple / medium / complex. Simple → GPT-4o-mini or Haiku; complex → GPT-4o or Sonnet 3.5. Cost saving 60–80% on simple-task traffic with minimal quality loss if the classifier is well-tuned.

Latency routing

Route time-sensitive requests (“live chat”) to the lowest-latency provider/region. Use EWMA of recent p50 latency per provider, measured at the gateway. Switch provider when EWMA exceeds SLO budget. Cache the EWMA in Redis (10-second TTL); don’t recompute per-request.

LiteLLM config — model group with capability tag filter
model_list:
  - model_name: vision-capable
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
    model_info: {supports_vision: true}

    litellm_params:
      model: openai/gpt-4o-mini
      api_key: os.environ/OPENAI_API_KEY
    model_info: {supports_vision: false, input_cost_per_token: 0.00000015}

A/B Routing — Shadow Traffic, Canary

Routing decisions are not just about cost and latency — they are also the mechanism for safely introducing new models into production. Three progressive rollout patterns apply.

Shadow
100% traffic → Model A (live)
100% traffic → Model B (shadow, response discarded)
Canary
95% traffic → Model A (control)
5% traffic → Model B (canary, response live)
A/B test
50% users → Model A (sticky)
50% users → Model B (sticky)
Full rollout
100% traffic → Model B (winner)

Implementation detail

Shadow traffic implementation

Fire the shadow request asynchronously (asyncio.create_task or a background queue). Do NOT await it on the critical path. Log the shadow response to a separate trace. Compare quality offline: automated eval (LLM-as-judge) on paired {prompt, A-response, B-response} triples.

Sticky assignment for A/B

Hash user_id + experiment_id to assign a user to a variant. Use a Bloom filter or Redis bitmap to record assignment; never re-roll. Sticky assignment is critical: if a user switches between variants mid-session, you contaminate both experimental groups.

Statistical power

LLM quality differences are small (1–5% on typical evals). You need sample sizes in the thousands before a difference is statistically significant at p<0.05. A/B tests with LLM evals require longer run windows than traditional latency A/B tests. Plan for at least 7 days at production traffic before drawing conclusions.

Hit-Rate Metrics & Cache Hygiene

A cache that nobody monitors is a cache that quietly stops working. Track these metrics continuously and set alerts on degradation.

MetricDefinitionAlert threshold
Exact cache hit ratehits / (hits + misses) over 1-hour windowAlert if <20% drop from 7-day baseline
Semantic cache hit ratesemantic hits / total requests (excludes exact hits)Alert if <expected rate for that route type
Prompt cache hit tokenscache_read_input_tokens / input_tokens per providerAlert if <50% on routes known to have long static prefixes
Cache cost saving((cached tokens × uncached price) - (cached tokens × cached price)) / dayAlert if savings drop >25% day-over-day
Semantic cache false positive rateFraction of cache hits that received a “wrong answer” eval scoreAlert if >2%

Cache hygiene operations

Invalidation triggers

  • Model version change — flush the entire cache namespace for that model
  • System prompt change — flush exact and semantic caches (prompt cache self-expires)
  • Knowledge cutoff — expire time-sensitive cached answers via per-entry TTL
  • Regulatory requirement — purge by user_id on erasure request

Warming strategies

  • Pre-populate semantic cache on deploy with synthetic question variants
  • Replay yesterday’s top-100 queries against the new cache after a flush
  • Prompt cache: send a warm-up request with the static prefix before routing live traffic
  • Measure cold-start latency and account for it in SLO calculations

What to Take Away

  • Three independent cache layers. Exact match (100% saving, zero cost), semantic match (100% saving, similarity risk), provider prompt cache (50–90% on prefix tokens).
  • Anthropic prompt cache: mark breakpoints with cache_control: ephemeral; minimum 1024 tokens; TTL 5 minutes; cache write costs 1.25×. Break-even at ~1.4 uses.
  • OpenAI prompt cache: automatic; 128-token granularity; 50% off cached tokens; put static content first, dynamic content last.
  • Semantic cache threshold matters. 0.97 cosine for factual queries; namespace by tenant; disable for personalised or time-sensitive routes.
  • RedisVL + HNSW gives <3 ms semantic cache lookups at 100 K scale; embed once, reuse for both retrieval and cache lookup.
  • Route by capability first (context window, vision), then cost, then latency. A query classifier sending simple tasks to cheap models saves 60–80% on that traffic segment.
  • Shadow → canary → A/B → full rollout. Run A/B for 7+ days; use sticky user assignment; compare with automated LLM-as-judge evals.
  • Monitor hit rates. Alert on >20% drops; flush caches on model version changes; purge by user ID for GDPR erasure.
